Case Study 2 — AWS Retail Event-Driven Data Platform

Business problem

An online retailer needs near-real-time visibility into orders, payments, and fulfillment. Batch exports are delayed, source events can arrive more than once, and analysts need a trusted daily sales model.

Architecture

Order application → EventBridge / Kinesis → SQS buffer → Lambda validation → S3 raw zone → Glue Data Catalog + Glue ETL → S3 curated Parquet → Athena / Redshift → QuickSight

Optional components:

  • Step Functions for multi-step orchestration.
  • CloudWatch for logs, alarms, and metrics.
  • Lake Formation for governed table and column access.
  • KMS for encryption; IAM roles for least-privilege access.

Data flow

  1. The order service publishes order-created and order-updated events.
  2. SQS buffers events and supports retry / dead-letter handling.
  3. Lambda validates the event envelope and writes immutable JSON to S3.
  4. Glue crawlers or explicit table definitions register raw data in the Glue Data Catalog.
  5. Glue Spark jobs standardize timestamps, currencies, status values, and customer/order keys.
  6. Curated data is stored as partitioned Parquet, typically by order date.
  7. Athena supports ad hoc analysis; Redshift serves governed, high-concurrency warehouse workloads.
  8. CloudWatch alarms on queue depth, DLQ messages, failed jobs, and data freshness.

Design decisions

  • At-least-once delivery: assume duplicate events; make transformations idempotent.
  • Schema evolution: version event schemas and quarantine unsupported versions.
  • Partitioning: choose partitions that align with common filters; avoid over-partitioning.
  • Small files: compact output files before large Athena scans.
  • Replay: retain raw events and support replay by event date or event ID.
  • Cost: use S3 lifecycle policies, Parquet compression, and partition pruning.

Data quality

Check unique order/event IDs, non-null order IDs, valid status transitions, positive item quantities, and reconciliation between order totals and item totals. Route invalid events to a quarantine prefix and preserve error reasons.

Interview walkthrough

Question: Why use SQS between events and processing? It decouples producers from consumers, absorbs traffic spikes, enables controlled retries, and supports a dead-letter queue for poison messages. Consumers can scale independently.

Question: How do you prevent duplicate orders? Use a stable event ID and business key, maintain a processed-event ledger or merge into a curated table, and make writes idempotent. Never assume the event bus delivers exactly once.

Portfolio implementation

Run python src/transform_retail_orders.py. It standardizes the synthetic order feed, removes duplicate event deliveries, quarantines invalid records, and creates a daily sales summary.

For AWS deployment, use an IAM execution role, S3 bucket encryption, Glue job bookmarks where appropriate, and CloudWatch alarms. Do not place AWS access keys in source code.
